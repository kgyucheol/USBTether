# 개발 일지

이 문서는 USBTether 가 왜 지금의 모양이 되었는지를 남긴 것입니다. 코드만 봐서는
알기 어려운 판단들 — 무엇을 시도했다 버렸는지, 어떤 전제가 틀렸는지, 어떤 버그를
어떻게 찾았는지 — 을 적었습니다.

읽는 순서대로 실제 개발 순서입니다.

<br>

## 출발점이 틀렸다

처음 받은 요구는 "USB 디버깅으로 폰에 SOCKS 프록시를 열어놨으니 노트북에서 쓰게
해달라" 였습니다. 기존 스크립트는 이렇게 동작하고 있었습니다.

```
adb forward tcp:8022 → 폰의 sshd
ssh -D 1080 로 SOCKS 터널 생성
```

그런데 동작하지 않았습니다. 확인해 보니:

```
kex_exchange_identification: Connection closed by remote host
```

폰의 8022 번 포트에는 아무것도 없었습니다. 폰에서 실제로 열려 있는 포트를 훑어보니
**프록시 앱이 SOCKS5 를 1080 에서 직접 서비스하고 있었습니다.**

```
tcp6  0  0  [::]:1080  [::]:*  LISTEN
```

즉 SSH 터널을 만들 이유가 처음부터 없었습니다. `adb forward tcp:1080 tcp:1080`
한 줄이면 끝나는 일이었습니다. ssh, sshpass, 평문 비밀번호가 전부 불필요했습니다.

**교훈**: 고쳐 달라는 것을 고치기 전에 그게 실제로 무슨 일을 하는지 확인한다.

<br>

## 프록시 설정만으로는 부족하다

`adb forward` 로 SOCKS 를 끌어온 뒤, 브라우저와 터미널에 프록시 주소를 알려주는
것까지는 쉬웠습니다. 문제는 그 다음이었습니다.

프록시 설정을 지원하지 않는 프로그램 — `apt`, `docker`, 게임, 각종 네이티브 앱 —
은 그대로 원래 회선으로 나갑니다. "노트북 인터넷을 폰으로" 라는 요구를 절반만
만족시킨 셈입니다.

그래서 커널 방화벽(nftables)에서 나가는 트래픽을 가로채는 투명 프록시로 방향을
바꿨습니다. 프로그램이 프록시를 몰라도, 프록시 설정 자체가 없어도 동작합니다.

<br>

## SOCKS5 는 UDP 를 나르지 못한다

투명 프록시를 만들기 전에 폰의 앱이 무엇을 할 수 있는지 직접 확인했습니다.

```
UDP ASSOCIATE : 코드 7 (명령 미지원)     → UDP 불가 확정
TCP CONNECT   : IPv4 / IPv6 / 도메인 모두 성공
TCP 53 포트   : 연결 성공, DNS 질의 응답 수신
```

UDP 를 못 나른다는 것은 **DNS 와 QUIC 이 막힌다**는 뜻입니다. 둘 다 UDP 니까요.
그런데 TCP 53 으로는 DNS 가 정상 동작했습니다. 여기서 구조가 정해졌습니다.

| 트래픽 | 처리 |
|---|---|
| TCP | 원래 목적지를 알아내 SOCKS5 로 중계 |
| DNS | **TCP DNS 로 변환**해 전달 |
| 나머지 UDP | 차단 (안 막으면 원래 회선으로 새어나감) |

QUIC 을 막으면 브라우저가 알아서 TCP(HTTP/2) 로 내려옵니다.

<br>

## 실제로 잡은 버그들

만들면서 잡은 것보다 **만든 뒤에 실측하다 잡은 것**이 훨씬 많았습니다.

### DNS 가 폰을 거치지 않고 있었다

터널이 잘 도는 것처럼 보였는데 DNS 통과 건수가 계속 0 이었습니다. 규칙을 보니
사설망 예외가 DNS 리다이렉트보다 **먼저** 걸려 있었습니다. 공유기 DNS 는 사설망
주소라서, 도메인 조회가 통째로 원래 회선으로 새어나가고 있었습니다.

순서를 바꿔 DNS 를 목적지와 무관하게 먼저 처리하도록 고쳤습니다.

### Wi-Fi 를 끄면 인터넷이 끊겼다

데이터는 USB 로 나가는데 Wi-Fi 가 필요한, 앞뒤가 안 맞는 상태였습니다.

원인은 방화벽이 가로채려면 **커널이 먼저 그 패킷을 보낼 경로를 찾아야** 한다는
점이었습니다. 기본 경로가 사라지면 `connect()` 가 즉시 실패하고, 가로챌 패킷 자체가
생기지 않습니다.

더미 인터페이스에 아주 낮은 우선순위의 기본 경로를 깔아 해결했습니다. 실제 회선이
있으면 그쪽이 쓰이고, 없으면 이 경로가 패킷을 받아 방화벽까지 흘려보냅니다.

### 연결이 열려 있으면 종료가 멎었다

서비스를 내리는 데 90 초가 걸리고 실패했습니다. `wait_closed()` 가 열려 있는 연결의
핸들러가 전부 끝나기를 기다리기 때문이었습니다. 살아 있는 연결을 먼저 끊고 최대
3 초만 기다리도록 고쳤습니다. 90 초 실패 → 2.6 초.

### 폰이 끊기면 인터넷이 통째로 멎은 채 방치됐다

폰이 `unauthorized` 로 떨어지면 USB 통로가 끊겨 모든 TCP 가 갈 곳을 잃습니다.
그런데 앱은 켜진 상태를 유지하며 방화벽 규칙만 남겼습니다. 30 초 넘게 끊기면
스스로 꺼져 원래 회선을 돌려주도록 했습니다.

### 감시 태스크가 자기 자신을 취소했다

위 기능을 만들다 발견했습니다. 감시 태스크가 스스로 `disable()` 을 부르면 그 안에서
자기를 취소해 정리가 중간에 끊기고, 최악의 경우 **방화벽 규칙만 남아** 인터넷이
끊긴 채로 남습니다.

### snap 갱신 보류가 조용히 실패했다

데이터 절약 기능을 만들고 로그를 보니 타이머만 멈추고 snap 은 언급이 없었습니다.
실패 사유를 `debug` 로 삼키고 있어서 원인을 알 수 없었습니다. `warning` 으로 올리자
바로 나왔습니다.

```
cannot add authorization: open /root/.snap/auth.json: permission denied
```

`ProtectHome=yes` 가 `/root` 를 막고 있었습니다. snap 클라이언트는 `$HOME` 설정을
무시하고 uid 로 홈을 찾습니다. `ProtectHome=tmpfs` 로 바꿔 해결했습니다. 사용자
홈이 보이지 않는 것은 마찬가지입니다.

**교훈**: 조용히 실패하는 코드를 남기지 않는다.

### 이름 풀이를 통째로 가져가고 있었다

"안 되는 곳만" 모드를 만들 때, 대체 경로가 모드와 무관하게 모든 이름 풀이를
가져가고 있었습니다. 전체 모드에서는 의도한 동작이지만, 원래 회선을 살려 두는
모드에서는 **그 망에서만 풀리는 이름이 통째로 안 풀립니다.**

이 모드의 제1원칙을 스스로 어긴 셈이라, 모드에 따라 나누도록 고쳤습니다.

## 설계 판단

### 데몬은 root 로 돈다

처음에는 전용 계정에 `CAP_NET_ADMIN` 만 주려 했습니다. 그런데 polkit 이 막았습니다.

```
Only trusted callers (e.g. uid 0 or an action owner) can use
CheckAuthorization() for subjects belonging to other identities
```

호출자가 uid 0 이 아니면 **다른 프로세스의 권한을 확인할 수 없습니다.** 즉
polkit 인증을 쓰려면 데몬이 root 여야 합니다.

대신 root 가 가질 수 있는 능력을 셋으로 제한했습니다. `CAP_DAC_OVERRIDE` 가 빠져
있어 파일 권한을 무시하지도 못합니다.

```
CapEff: 0000000000003400   →  NET_BIND_SERVICE, NET_ADMIN, NET_RAW
```

### 작업 표시줄 아이콘은 별도 프로세스다

AppIndicator 는 GTK3 전용이라 GTK4 로 만든 창과 한 프로세스에 올릴 수 없습니다.

```
Requiring namespace 'Gtk' version '3.0', but '4.0' is already loaded
```

트레이만 떼어 작은 프로세스로 돌립니다. 창을 다시 열 때는 GApplication 이 같은 앱
ID 를 보고 기존 창을 앞으로 올려 주므로, 숨겨둔 창이 그대로 돌아옵니다.

### 판정 결과는 커널에 넣는다

"안 되는 곳만" 모드에서 모든 연결이 파이썬 프록시를 통과하면 그만큼 느려집니다.
그래서 한 번 판정된 목적지는 nftables 집합에 넣어 커널이 바로 처리하도록 했습니다.
판정이 끝난 뒤에는 속도 손해가 없습니다.

프록시가 직접 내보내는 연결에는 표식(`SO_MARK`)을 찍습니다. 이게 없으면 방화벽이
그 연결마저 다시 프록시로 돌려보내 자기 자신에게 무한히 되돌아옵니다.

### 자동 업데이트 목록을 하드코딩하지 않는다

처음에는 떠오르는 대로 4 개를 적었습니다. 시스템을 실제로 훑어 보니 9 개가
나왔고, 그중에는 예상하지 못한 것들이 있었습니다. 시스템마다 깔린 것이 다르므로
설치된 타이머를 찾아내고, 무엇을 보류할지는 사용자가 고르게 했습니다.

**사람이 직접 시작한 업데이트는 막지 않습니다.** 보류하는 것은 예약된 자동
실행뿐입니다. 모바일 회선으로 업데이트를 받고 싶은 사람도 있기 때문입니다.

<br>

## 만들다 버린 것

### 재시작 후 터널 자동 복구

패키지를 업그레이드하면 데몬이 재시작되면서 터널이 꺼집니다. Wi-Fi 없이 쓰는
중이라면 그 순간 인터넷이 통째로 사라집니다. 그래서 재시작 전 상태를 기억했다
되살리는 기능을 만들었습니다.

`/run` 에 표시를 남기는 방식이었는데 동작하지 않았습니다. `RuntimeDirectory` 는
서비스가 멈출 때 systemd 가 통째로 지웁니다. `RuntimeDirectoryPreserve=restart`
로 고치면 되는 문제였지만, 여기서 멈췄습니다.

**사용자 조작 없이 방화벽 규칙이 켜지는 것**은 부담이 큰 동작인데, 이를 정당화할
만큼 자주 일어나는 일이 아니었습니다. 애초에 개발 중 반복 설치 때문에 부각된
문제였습니다. 기능을 통째로 되돌렸습니다.

<br>

## 남은 한계

정직하게 적습니다.

- **UDP 는 중계되지 않습니다.** 폰의 SOCKS5 앱이 UDP ASSOCIATE 를 지원하지 않기
  때문입니다. 화상통화나 일부 게임은 동작하지 않습니다.
- **ping 은 원래 회선으로 나갑니다.** SOCKS 가 ICMP 를 나를 수 없습니다. 막을 수는
  있지만(`block_icmp_leak`) 그러면 ping 자체가 안 됩니다.
- **자동 판정이 놓치는 경우가 있습니다.** 차단 페이지가 정상 응답으로 돌아오는
  방식이면 연결 자체는 성공하므로 막힌 줄 모릅니다.
- **속도는 파이썬 프록시에 좌우됩니다.** 아주 높은 처리량에서는 병목이 될 수
  있습니다.
- **무엇이 벌어지는지 앱에서 잘 안 보입니다.** 어디가 폰으로 갔는지, 왜 느렸는지
  알려면 지금은 문서를 읽어야 합니다. 개선 여지가 가장 큰 부분입니다.
